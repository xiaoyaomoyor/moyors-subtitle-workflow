## 结论与建议顺序

不建议整包合并或按上游提交逐个机械移植。目标版本混合了可靠性修复、大量前端重组，以及面向 MAW 的口播整理、标记、字幕样式和导出流程；MSW 的 v4 多轨工程是独立实现。

建议先实施 A1–A4 可靠性修复，再实施 B1–B3 小范围工作流改进，最后做 MSW 回归和发布准备。C 类新功能另行确认范围，不作为此次跟进的必要条件。以下均为筛选建议，不是本轮实现清单。

## A. 优先吸收的可靠性修复

### A1. 本地 LLM 的 JSON 兼容

- 上游：兼容不接受 `json_object`、只接受 `json_schema` 或只接受普通文本的接口；按端点和模型记忆约束能力；过滤正文混入的思考内容，并对少数 JSON 尾部格式错误做保守修复。
- MSW：`maw/postprocess_llm.py::_request_completion` 仍固定提交 `json_object`，`_response_content` 不剥离正文中的 `<think>`。Launcher 的连接测试、模型列表和运行入口仍无条件要求非空 Key，虽然底层已有本机地址校验。
- 建议：吸收约束协商、思考内容处理和有界格式修复；本机接口免 Key 贯通上述入口，仅用于受支持的本机地址，不放宽云端接口要求。兼容回退只针对明确的协议不支持，保留 MSW 的重试上限、取消、翻译完整性校验和输出大小限制。
- 不能把补 JSON 括号扩展成猜测缺失字幕内容；语义或覆盖校验失败仍须明确失败，不采用跳过失败批次后静默生成残缺结果的方式。
- 证据：固定格式请求和入口限制已静态确认；合成的 `<think>…</think>` 加 JSON 响应在当前解析流程中不能被正常接受。未连接真实 LLM 服务。
- 来源：[JSON 约束与思考内容](https://github.com/Moyf/moys-asr-workflow/commit/eb78214f0536deb69b25beb916ed87763b13058b)、[Schema 降级与尾部修复](https://github.com/Moyf/moys-asr-workflow/commit/0c7a366720a49c9f1a189afbacc28f36322006eb)。

### A2. 基础波形的多声道反相抵消

- 上游：生成轻量波形时保留声道，按时间窗口取各声道的极值，避免先混为单声道导致左右声道抵消。
- MSW：`maw/waveform.py::extract_waveform` 仍使用 `-ac 1`。已有 QPK/多级缓存和其他峰值读取路径，因此问题范围是基础生成及兜底路径，不是所有 MSW 波形。
- 实际诊断：生成两秒左右声道互为反相的 PCM，原始采样峰值为 20000；当前基础生成结果的峰值为 0。此问题已复现。
- 建议：只调整基础采样聚合，保留 MSW 波形格式、媒体指纹、音轨选择、分辨率和缩放逻辑；时长按音频帧计算。实施时处理旧兜底缓存的失效策略，避免修复后继续命中旧平线缓存。
- 来源：[改善多声道轻量波形显示](https://github.com/Moyf/moys-asr-workflow/commit/1e20d42758c4c294ca4ba6fe0fea313dbab63829)。

### A3. Linux 打包版调用宿主运行时

- 适用范围：Linux 发行包；Windows 本机不受这项动态库路径问题影响。
- 上游：冻结包调用宿主 Python、pip、venv 等外部程序时恢复宿主动态库搜索路径，避免继承包内旧动态库；同时补全子进程实际需要读取的 Python 源文件。
- MSW：`maw/runtimes/base.py`、`maw/local_runtime.py`、`maw/ocr_runtime.py` 仍直接继承进程环境。`MSW.spec` 有 `maw.moss_runtime`、`maw.runtimes.freezer` 的隐藏导入，但未将对应源码补入供外部解释器使用的运行时目录；隐藏导入不能替代该目录中的源码。
- 建议：集中提供仅适用于冻结 Linux 宿主调用的环境处理，检查本地 ASR、OCR、TTS 等实际调用点。不要全局改父进程环境，也不要机械套用到依赖包内库的 Qt/FFmpeg 进程。
- 证据：环境继承及打包清单缺口已静态确认，模拟环境仍保留包内库路径。未在真实 Linux 打包产物运行验证，不能声称已复现具体机器上的启动失败。
- 来源：[宿主库路径修复](https://github.com/Moyf/moys-asr-workflow/commit/ac58a5eea4fd5f9639525aad334d9c36f7d73cb0)、[运行时源文件及后续修复](https://github.com/Moyf/moys-asr-workflow/commit/5d83137e9a3498e6fd870748eb43c01a5b712e65)。

### A4. ASR 错误提示和当前任务密钥脱敏

- 上游：识别明显的 Key 粘贴错误，区分认证、权限、限流、端点、网络和服务端错误；为空转写结果提供针对性提示；使用本次任务 Key 对错误文本做替换脱敏。
- MSW 已有保护：编辑器 `maw/msw/asr_config.py` 有 Key 校验，`maw/msw/asr.py` 和 `maw/local_log.py` 已有错误清理与脱敏，不能概括为整个项目没有这些能力。
- 剩余差异：Launcher 从配置回退读取的 Key 可能保留空白，现有非空判断仍会通过；`maw/gui_workflow.py::run_transcription` 主要检查进程和输出文件；`maw/launcher_batch.py` 将 `str(error)` 放入任务结果，缺少按本次 Key 做最终文本脱敏这一层。
- 建议：复用 MSW 现有保护，将 Launcher、批处理与编辑器的错误分类和脱敏口径统一；避免增加严格的供应商 Key 前缀规则。空结果提示利用已有媒体探测区分无音轨、提取失败和未识别到内容，不额外对整段媒体做静音扫描。
- 证据：合成空白 Key 在当前配置读取与非空判定中仍为真；其余为路径静态核对，没有调用云端 ASR，也没有使用真实密钥。
- 来源：[API 友好报错与空结果提示](https://github.com/Moyf/moys-asr-workflow/commit/014689275dd5bec7738ece7b1175550494dc3cc1)。
